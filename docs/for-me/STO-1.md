# [STO-1] 저장소 핵심        커밋: 355e00c..(이 문서 커밋)

## 한 줄 요약
프록시가 알려 주는 "요청 시작"과 "요청 끝(기록)"을 메모리에 모아 두는 저장소를 만들었다. 대시보드에는 **본문 없는 요약**으로 알리고, 하나를 고르면 **본문까지 복사한 사본**을 준다. 아직 프록시에 연결하지는 않았다(STO-4).

## 무엇이 어떻게 움직이나
```
 프록시 ── 시작 알림(id 7, GET /a) ──▶ addStart ──▶ 항목 7 = 진행 중 ──▶ 알림 { type: 'start', summary }
 프록시 ── 기록(id 7, 200, 본문…) ──▶ addFlow  ──▶ 항목 7 = 완료   ──▶ 알림 { type: 'done',  summary }
                                                     │
                       list()  ◀── 요약 목록(id 순) ──┤   요약 예: { id: 7, runId: 'c1f0…', state: 'done', method: 'GET',
                       get(7)  ◀── 상세 사본 ─────────┘            url: 'http://example.test/a', status: 200, statusFrom: 'upstream',
                                                                   durationMs: 12, requestSize: 0, responseSize: 5 }
```
- **요약에는 본문·헤더(쿠키)가 없다.** 1MiB 본문 기록 1,000건의 목록도 JSON으로 약 32만 자(건당 319자)다 [확인됨: `node scripts/probe/sto1-summary-size.mjs`]. 본문을 그대로 실으면 건당 400만 자가 넘는다(sto-cases A9).
- **상태 코드의 출처**: 목적지가 답했으면 `statusFrom: 'upstream'`, 목적지에 닿지 못해 프록시가 502 같은 응답을 직접 만들었으면 `statusFrom: 'proxy'`(결정 S-3).
- **CONNECT**: HTTPS 복호화 터널은 끝 기록이 오지 않아서 시작 알림은 넣지 않는다. 복호화하지 않는 터널은 끝날 때 요약(바이트 수)이 들어온다(결정 S-2).

## 지키는 약속 (테스트 18개)
| 약속 | 왜 |
|---|---|
| 시작 없이 끝만 와도 저장, 끝난 뒤 늦게 온 시작은 무시 | 프록시의 시작 알림은 사라질 수 있다(시작 구독자 오류, X4). 완료가 "진행 중"으로 되돌아가면 안 된다 |
| "모두 지우기" 전에 시작한 요청의 늦은 끝은 버림 | 지웠는데 다시 나타나면 헷갈린다(결정 S-5) |
| 목록은 id 순 | 끝나는 순서는 들쭉날쭉하다. 시각(startedAt)은 같은 ms·시계 변경에 흔들린다 |
| 요약·상세는 매번 새 사본, 상세 본문은 자기 메모리 | 받은 쪽이 고쳐도 저장된 기록·다른 구독자에게 번지지 않는다. `Buffer.from`으로 복사하면 작은 본문이 공유 풀(64KB)에 들어가 다른 기록의 바이트에 닿을 수 있다(sto-cases C10) |
| 구독자가 오류를 내도(동기 throw, 비동기 reject) 다른 구독자·저장·프록시는 그대로, 출력 없음 | 처리 안 된 reject 하나로 프로그램 전체가 꺼질 수 있었다 [확인됨: sto-cases E19]. 오류에 쿠키가 들어 있을 수 있어 찍지 않는다 |
| 알림 중에 구독 추가·해제, 저장소 조작을 해도 순서가 지켜짐 | 알림 중에 생긴 알림은 줄을 세워 지금 알림이 다 간 뒤에 보낸다 |
| 해제한 구독자·끝난 요청의 시작 알림을 붙잡지 않음 | 메모리가 풀리는지 테스트에서 가비지 컬렉션을 돌려 확인한다 |
| `console.log(store)`·JSON으로 찍어도 기록 내용이 나오지 않음 | 디버깅하다 쿠키가 터미널에 찍히는 일을 막는다 |

## 이번에 하지 않은 것
- 보관 상한(256MiB·10,000건) → STO-2. 지금은 끝없이 쌓인다.
- 필터(`list({ host, method, status })`) → STO-3. 지금은 인자를 무시한다.
- 프록시 연결 → STO-4. 그래서 이 단위는 실제 클라이언트(curl·브라우저) 실측이 없다 — 저장소에는 아직 실제 클라이언트가 닿지 않는다. STO-4에서 실측한다(O31).
