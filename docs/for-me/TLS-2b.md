# [TLS-2b] CA 보관 견고성: 쓰기 도중 실패, 동시 실행, 남은 임시 파일, 심어 둔 링크, 키 파일 권한        커밋: 6eb9f70..(이 문서 커밋)

## 한 줄 요약
루트 CA를 **만드는 순간**에 생길 수 있는 사고를 막았다. 도중에 실패해도 반쪽 CA가 남지 않고, 두 프로그램이 동시에 만들어도 같은 CA를 받고, 개인키 파일은 **내 계정만** 읽을 수 있다. TLS-2 때는 SYSTEM과 Administrators도 읽을 수 있었다.

## 만드는 순서
웹 개발로 치면 "임시 파일에 다 쓴 뒤 한 번에 교체"하는 배포 방식과 같다. 다만 Windows의 `rename`은 **이미 있는 파일을 덮어써서**(실측 E77) 두 프로그램이 동시에 만들면 서로의 키를 덮을 수 있다. 그래서 대신 **하드 링크**를 쓴다. 하드 링크는 같은 파일에 이름을 하나 더 붙이는 것이고, 그 이름이 이미 있으면 실패한다(E78).

```
① ca-key.pem.<pid>-<난수>.tmp 를 빈 채로 만든다
② 그 파일의 권한을 "나만"으로 바꾼다            ← 키를 쓰기 "전에"
③ 키·인증서 내용을 임시 파일에 쓴다
④ 하드 링크로 ca-key.pem 자리를 잡는다          ← 이미 있으면 "진 것": 이긴 쪽의 CA를 기다렸다가 읽는다
⑤ 하드 링크로 ca-cert.pem 자리를 잡는다
⑥ 임시 파일 이름을 지운다(내용은 ④⑤의 이름으로 남음)
중간에 실패하면: ④에서 놓은 키를 지우고 임시 파일도 지운다 → 폴더에 아무것도 남지 않는다
```

| 사례 | 상황 | 결과 |
|---|---|---|
| 28·29 | 인증서를 반쯤 쓰다 실패 / 인증서 자리 잡기 실패 / 키 쓰기 실패 | `CA_WRITE`, 폴더가 비어 있고 다음 실행은 정상 |
| 38 | 권한 설정 실패 | `CA_ACL`, **키를 쓰지 않는다**(실패하면 닫힘) |
| 30 | 같은 프로그램에서 5번 동시에 / 다른 프로그램 2개가 동시에 | 모두 같은 CA, 디스크와 같음 |
| 31 | 지난번에 남은 임시 파일 | 60초 넘은 것은 지우고, 최근 것(다른 프로그램이 쓰는 중일 수 있음)과 남의 파일은 그대로. 임시 파일을 CA로 쓰지 않는다 |
| 35 | `ca-key.pem` 자리에 누군가 심어 둔 정션(다른 폴더로 가는 길) | `CA_NOT_FILE`. 따라가서 쓰지 않는다 |

**남는 위험**: ④와 ⑤ 사이에 프로그램이 강제 종료되면 키만 남는다. 그러면 다음 실행은 "한쪽만 있음"(`CA_INCOMPLETE`)으로 멈춘다. 지난번에 정하신 "깨지면 멈추고 알림" 그대로다.

## 키 파일 권한: 생각보다 까다로웠다
Windows 파일에는 "누가 무엇을 할 수 있는지" 목록(ACL)이 붙는다. 보통은 폴더의 목록을 물려받는다(상속).

1. 처음 예상: `icacls 파일 /inheritance:r /grant:r 나:(F)`(상속 끊기 + 나에게 모든 권한)면 나만 남는다.
2. **실측 결과는 달랐다(E79 불일치)**: SYSTEM과 Administrators가 그대로 남았다. 물려받은 것이 아니라 파일에 직접 붙은 권한이라 "상속 끊기"로는 지워지지 않았다.
3. 목록을 통째로 덮어쓰는 `icacls /restore`는 **관리자 특권이 필요해** 실패했다(종료 코드 1300).
4. 쓴 방법: `icacls /save`로 남은 목록을 읽는다. 이 목록은 계정을 이름이 아니라 SID(계정 고유 번호)로 적어서 한글 Windows에서도 똑같이 읽힌다. 나 아닌 계정을 하나씩 지운 뒤 **다시 읽어서** 정말 나 하나만 남았는지 확인하고, 아니면 멈춘다.

실제 결과(`node scripts/probe/tls2-tools.mjs`):
```
TLS-2:   ca-key.pem NT AUTHORITY\SYSTEM:(F)  BUILTIN\Administrators:(F)  wooni\wooni:(F)
TLS-2b:  ca-key.pem wooni\wooni:(F)
```
인증서(`ca-cert.pem`)는 공개 정보라 제한하지 않는다.

### 예상 밖: 이름이 같은 다른 프로그램
처음 실측에서 `whoami`를 불렀더니 Windows의 `whoami.exe`가 아니라 **Git Bash에 들어 있는 같은 이름의 프로그램**이 실행됐다. PATH(프로그램을 찾는 폴더 목록)에서 먼저 잡혔기 때문이다. 보안 설정을 하는 프로그램이 엉뚱한 것으로 바뀌면 안 되므로, Windows 도구는 `C:\Windows\System32\...` 절대 경로로 부른다. 테스트는 PATH를 비운 채로도 확인한다.
