# [UI-4] 실시간 통로(SSE)        커밋: bdf5e89..(이 문서 커밋)

## 한 줄 요약
대시보드가 **새 요청이 생길 때마다 바로 알려 주는 통로**(`GET /api/events`)가 생겼습니다. 화면(UI-5)은 아직 없어서 지금은 curl로만 볼 수 있습니다. 이 통로도 UI-1의 검사(Host·Origin·토큰)를 먼저 통과해야 합니다.

## SSE가 뭔가요
- **SSE(Server-Sent Events)**: 서버가 응답을 끝내지 않고 열어 둔 채, 일이 생길 때마다 글 한 덩어리씩 흘려보내는 방식입니다. 웹 개발에서 쓰는 `EventSource`가 이것을 읽습니다.
- 우리는 `EventSource` 대신 **`fetch` 스트림으로 읽습니다**(D-4). `EventSource`는 `Authorization` 헤더를 붙일 수 없기 때문입니다. 토큰을 URL에 넣으면 기록·기록 창에 남습니다(U43).
- WebSocket은 쓰지 않습니다. WebSocket은 브라우저가 다른 사이트에서도 연결을 열어 주어서(CSWSH, U3) 따로 막아야 할 것이 늘어납니다.

## 흐르는 내용
```
data: {"type":"hello","runId":"cfdbb0986f294fb6"}          ← 연결하자마자 한 번

id: 1
data: {"type":"start","summary":{"id":1,"state":"pending","method":"POST","url":"http://127.0.0.1:18090/x",…}}

id: 2
data: {"type":"done","summary":{"id":1,"state":"done","status":200,"durationMs":29.4,…}}

: ping                                                       ← 15초마다(하트비트)
```
- 알림 종류: `start`(요청 시작), `done`(완료), `evicted`(상한으로 빠진 기록 id들), `cleared`(모두 지움). 요약만 있고 **쿠키·헤더·본문은 없습니다**. 보려면 UI-3의 상세·본문 API를 씁니다.
- `id: <n>`은 이 실행에서 보낸 알림의 순번입니다(기록 id와 다름).

## 왜 이렇게 만들었나
| 문제 | 한 일 |
|---|---|
| 연결을 끝없이 열어 메모리를 채움(U32) | 동시에 **16개**까지. 더 오면 503 + 고정 문구("쓰지 않는 탭을 닫으세요"). 이미 열린 연결을 끊지는 않습니다 |
| 검사 전에 자리를 차지함(U32) | 토큰·출처 검사를 **통과한 GET만** 자리를 받습니다. 거절된 요청은 자리를 쓰지 않습니다 |
| 읽지 않는 연결에 쌓이는 데이터(U33) | 보내지 못하고 쌓인 양이 **1MiB**를 넘으면 그 연결만 끊습니다. 화면은 다시 연결하면 됩니다 |
| 알림을 보내느라 프록시가 느려짐(U38, STO 결정 1) | 저장소의 알림을 **줄에 세워 두고 바로 돌아옵니다**. 실제 쓰기는 잠시 뒤 한 번에, 연결이 여럿이어도 JSON 변환은 한 번만 |
| 끊겼다 다시 연결(U34) | 지난 알림을 다시 보내지 않습니다. 대신 연결마다 `hello`가 먼저 오고, 화면은 그때 목록을 API로 다시 받습니다. `runId`가 바뀌었으면 프로그램이 새로 시작된 것입니다(F10) |
| 몇 시간 열어 둠(F8) | 15초마다 `: ping`. 40초 동안 열어 두어도 끊기지 않는 것을 확인했습니다 |
| 브라우저의 "출처당 6연결"(U36) | 서버로는 막을 수 없습니다(브라우저 규칙). 화면은 탭마다 통로 하나만 엽니다 → UI-5에서 지킴 |

## 실제로 해 본 것 (curl, `npm.cmd start -- --port 18080`, 목적지는 127.0.0.1:18090의 작은 서버)
| 명령 | 결과 |
|---|---|
| `curl.exe -s -N -i -m 4 -H "Authorization: Bearer <토큰>" http://127.0.0.1:18081/api/events`(백그라운드로 열어 둠) | 200, `text/event-stream; charset=utf-8`, `no-store`·`nosniff` 등 보안 헤더 |
| 그동안 `curl.exe -x http://127.0.0.1:18080 -H "Cookie: k=CURL-COOKIE" --data-binary curl-body http://127.0.0.1:18090/x` | `upstream-saw:curl-body`. 스트림에 hello → start(id 1) → done(id 1, 200). `CURL-COOKIE`·`curl-body`는 0번 |
| 토큰 없이 `/api/events` | 401 |
| `curl.exe -s -N -m 40 …/api/events` | 40초 동안 열림, `: ping` 두 번(curl이 스스로 40초에 끝냄) |

## 이 PR에서 생긴 일 (솔직하게)
- **구현 중 테스트 하나 실패 → 원인 찾고 고침**: "느린 연결만 끊는다" 테스트가 실패했습니다. 쌓인 양을 **쓴 뒤에** 재서, 한 번에 많이 쓰면 잘 읽는 연결까지 끊었습니다. **쓰기 전에** 재도록 고쳤습니다(`933474f`).
