# [PRX-1c] 목적지 쪽·견고성: 응답 없는 서버, 큰 데이터, 이상한 응답        커밋: 3ec846e..(이 문서 커밋)

## 한 줄 요약
프록시의 **다른 쪽 끝(목적지 서버)**이 이상하게 굴 때를 다뤘다. 응답을 안 하거나, 도중에 끊거나, 깨진 응답을 보내거나, 프로토콜을 바꾸자고(101) 할 때다. 34개 사례 중 28개는 이미 올바르게 동작했고, 6개를 새로 고쳤다.

## 새로 고친 6가지 (실측으로 찾음)

| 사례 | 고치기 전 (실측) | 고친 뒤 | 왜 문제였나 |
|---|---|---|---|
| A9 다른 프로그램이 `0.0.0.0:P`를 쓰는 중 시작 | **오류 없이 시작됨** — Windows가 같은 포트를 나눠 쓰게 허용 | 시작하지 않음(EADDRINUSE) | 브라우저 트래픽이 어느 프로그램으로 갈지 예측할 수 없다 |
| B3 `0.0.0.0:P`, `localhost.:P` | 400 "absolute-form만…" | 508 루프 | 무한 반복은 없었지만, 진짜 원인(루프)이 가려졌다 |
| B8 목적지가 응답을 안 함 | **끝없이 기다림** | 504 (기본 30초) | 연결이 쌓이면 결국 프록시가 멈춘다 |
| D17 헤더를 아주 느리게 보냄 | 60초 넘게 기다림 | 408 (기본 30초) | 버그 있는 클라이언트 하나가 연결을 붙잡는다 |
| E7 목적지가 101 응답 | **클라이언트에 아무 응답 없음(멈춤)** | 502 | 터널로 바뀌면 기록·검사를 벗어난 통로가 생긴다 |

A9를 막을 때 버린 방법이 있다: 시작하기 전에 `0.0.0.0`에 잠깐 바인딩해 보는 것. 이렇게 하면 **Windows 방화벽 "액세스 허용" 창이 뜰 수 있다.** 검토자가 "무심코 허용을 누르면 외부에 열린다"고 경고한 바로 그 상황이다. 그래서 대신 **그 포트로 접속해 보고, 누가 응답하면 시작하지 않는다.**

## 큰 데이터 실측 (`node scripts/probe/prx1c-stream.mjs <MB>`)
프록시를 별도 프로세스로 띄우고 curl로 받으면서 프록시의 최대 메모리를 쟀다.

| 중계한 본문 | 프록시 최대 메모리 (시작 61MB) | 시간 |
|---|---|---|
| 64MB | 96MB | 0.3초 |
| 512MB | 142MB | 1.6초 |
| 2GB | 162MB | 5.9초 |

본문이 32배 커져도 메모리는 거의 그대로다. **본문을 메모리에 모으지 않고 흘려보낸다(스트리밍)**는 증거다. 웹 개발로 치면 파일 업로드를 `req.body`로 통째로 받지 않고 `pipe`하는 것과 같다.

## 이미 잘 되던 것 (회귀 테스트로 고정한 28개 중 일부)
- LAN 주소(192.168.x.x)로는 접속 자체가 안 된다 → 127.0.0.1 바인딩이 실제로 효과가 있다는 확인
- 목적지가 깨진 응답(상태줄 없음, CL+TE 함께)을 보내면 502. Node의 응답 파서가 막는다
- 목적지가 응답 도중 끊으면, 클라이언트에게 "다 받은 것처럼" 보이지 않게 연결을 끊는다
- `HTTP_PROXY` 환경 변수가 프록시 자신을 가리켜도 루프가 생기지 않는다
- 20MB 업로드·다운로드의 바이트가 정확히 같다(SHA-256 비교)
