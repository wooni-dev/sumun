# [TLS-1b] 터널 견고성: 반쪽 닫기, 대용량, 연결 타임아웃, 동시 300개, 종료        커밋: 2064e4d..(이 문서 커밋)

## 한 줄 요약
TLS-1에서 만든 CONNECT 터널을 "이상한 상황"에서 시험했다. 대부분은 이미 잘 됐고, **한 가지 결함**(목적지가 먼저 "나는 다 보냈어"라고 하면 그 뒤 브라우저가 보낸 데이터가 사라지고 기록도 남지 않음)을 찾아 고쳤다. 코드 변경은 몇 줄이다.

## 반쪽 닫기(half-close)란
TCP 연결은 **두 방향의 통로**다. 한쪽이 "나는 더 보낼 게 없어"(FIN)라고 해도, 반대 방향은 계속 열려 있을 수 있다. 웹 개발로 치면, 요청 본문을 다 올린 뒤 업로드 스트림만 닫고 응답은 계속 기다리는 것과 비슷하다.

```
 클라이언트 ──▶ 프록시 ──▶ 목적지
            ◀──        ◀── "greeting" 그리고 FIN(나는 다 보냈어)
 클라이언트 ── "after-fin" ──▶ ?
```

고치기 전에는 Node의 기본 설정(`allowHalfOpen: false`) 때문에, 프록시가 목적지의 FIN을 받는 순간 **목적지 쪽 연결을 통째로 닫았다.** 그러면:
1. 클라이언트가 그 뒤 보낸 `after-fin`은 목적지에 닿지 않았다.
2. 두 소켓을 이어 주던 `pipe`가 풀리면서 클라이언트 쪽 소켓이 읽기를 멈췄다. 그래서 클라이언트가 닫아도 프록시가 그것을 알아채지 못했고, **터널 기록이 영영 나오지 않았다**(사례 S2 "기록 정확히 1개" 위반).

고친 것: 목적지에 연결할 때 `allowHalfOpen: true`. 이제 FIN은 반대쪽에 그대로 전달되고(결정 6 "해석하지 않는다"), 양쪽이 모두 닫혀야 터널이 끝난다.

실측(고치기 전, `node scripts/probe/tls1b-halfclose.mjs`):
```
E61 R6b 목적지 먼저 FIN: 클라이언트가 받은 것="greeting" ... / 목적지가 받은 것="" ... / 기록 0개
E61 R6b 2초 더 기다린 뒤: 기록 0개, 클라이언트 closed=true
```
원인 재현(`node scripts/probe/tls1b-leak.mjs`): 마지막 줄 `client-side destroyed false` — 프록시의 클라이언트 쪽 소켓이 남아 있다.

## 연결 타임아웃(R8)과 "연결 함수 주입"
응답하지 않는 서버(방화벽이 SYN을 버리는 곳)로 CONNECT하면, 프록시는 `upstreamTimeoutMs`(기본 30초) 뒤 **504**를 돌려준다. 이 동작은 TLS-1에 이미 있었지만, 자동 테스트로 확인하려면 "연결이 끝나지 않는 서버"가 필요하다. 로컬에서는 만들 수 없어서(로컬 서버는 바로 연결을 받는다) `startProxy({ connectUpstream })`으로 **연결 함수를 바꿔 끼울 수 있게** 했다. 테스트는 영영 연결되지 않는 소켓을 넘긴다. 기본값은 `net.connect` 그대로다. (`lookup` 옵션과 같은 방식)

실제 curl로도 확인(`node scripts/probe/tls1b-curl.mjs`, 타임아웃 2초로 줄인 프록시):
```
E68 응답 없는 주소: CONNECT 504  2.0초
```

## 이미 잘 되던 것 (회귀 테스트로 고정)
| 사례 | 확인한 것 | 결과 |
|---|---|---|
| R6a | 클라이언트가 먼저 FIN → 목적지가 받고 나서 답함 | 답이 끝까지 온다 |
| R7 | 양방향 50MB 동시 | sha256 동일, 기록 바이트 수 정확 |
| R7 | 클라이언트가 읽기를 멈춤 | 목적지도 멈춘다(쌓인 양 1.3MB 실측, 상한 8MB). Node의 `pipe`가 **역압**(받는 쪽이 느리면 보내는 쪽을 멈춤)을 해 준다 |
| R12 | 동시 터널 300개 | 섞이지 않음, 기록 300개 |
| R13 | 열린 터널 20개가 있는 채로 `close()` | 62ms에 끝남 |

실제 curl(100MB 다운로드·업로드): 바이트 정확, 프록시 메모리 69MB → 126MB. 300MB로 재면 151MB — **본문이 3배여도 메모리는 22MB만 늘어** 본문을 메모리에 모으지 않는다는 뜻이다.

## 예상 밖이었던 것: 이 PC는 한순간에 몰린 연결을 약 232개만 받는다
처음엔 300개를 같은 순간에 열었더니 68개가 실패했다. 프록시 결함인지 보려고 **프록시 없이** 시험 서버에 바로 300개를 열었더니 똑같이 232개만 성공했다(`node scripts/probe/tls1b-concurrency.mjs 300 direct`). 대기열 크기(backlog)를 1024로 올려도 같았다(`tls1b-backlog.mjs`). 그래서 **OS의 한계**로 판단했다 [추측: Windows가 대기열을 약 200으로 자름]. 테스트는 50개씩 열어서 300개가 모두 열린 상태로 검사한다.
- 프록시 자신도 같은 한계가 있다. 브라우저는 이렇게 한순간에 수백 개를 열지 않으므로 지금은 고치지 않는다(범위 밖 기록).
