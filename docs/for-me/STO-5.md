# [STO-5] 오래 걸리는 요청 보호와 필터 오타 오류        커밋: eaa95c5..(이 문서 커밋)

## 한 줄 요약
STO 보고서의 결정 두 가지를 고쳤다. ① 메모리(바이트) 상한에 걸리면 이제 **끝난 기록부터** 뺀다. 그래서 큰 다운로드나 실시간 스트림처럼 오래 걸리는 요청이 진행 중에 사라지지 않는다(결정 2, R2). ② 필터에 **모르는 조건 이름**(`{ hots: 'x' }` 같은 오타)을 넣으면 조용히 전체 목록을 주지 않고 오류를 낸다(결정 7, R7). 이 단위로 STO 큰 단위가 ✅가 됐다.

## ① 바이트 상한: 완료 먼저, 그다음 진행 중
```
 전:  [진행 중 1(큰 다운로드)] [완료 2] [완료 3] ← 넘침 → 1이 가장 오래돼서 먼저 빠짐 → 1이 끝나도 기록 버림
 후:  [진행 중 1(큰 다운로드)] [완료 2] [완료 3] ← 넘침 → 완료 2가 빠짐           → 1이 끝나면 정상 저장
```
- 규칙: 먼저 들어온 **완료**부터 뺀다. 방금 넣은 것 말고 남길 완료가 하나도 없는데도 넘칠 때만 진행 중을 뺀다.
- 왜 "진행 중은 절대 안 뺀다"가 아닌가: 보고서 결정 2 ①을 글자 그대로 따르면 STO-2 테스트("진행 중만 쌓여도 바이트 상한으로 빠진다")를 고쳐야 했다. 이번 세션에 다시 여쭈었고, 답은 **"완료 먼저, 그다음 진행 중"**이었다.
- 실제로는 ①과 같다 [추측: 계산]: 기록 하나는 본문이 쪽마다 1MiB까지라 완료 하나는 약 2MiB 이하이고, 요청 헤더는 16KB까지라 진행 중 1,000개를 다 모아도 약 33MB다. 256MiB 상한에서 진행 중이 빠지려면 완료가 하나도 없어야 하는데, 그럴 수 없다.

## ② 모르는 조건 이름은 오류
| 입력 | 전 | 후 |
|---|---|---|
| `store.list({ hots: 'example.com' })` | 조건을 무시하고 **전체 목록** | `TypeError: 필터 조건 이름을 알 수 없습니다.` |
| `store.list({ host: 'example.com', Method: 'GET' })` | Method를 무시 | TypeError(대소문자도 정확히) |
| `store.list({ host: '', method: undefined })` | 전체 | 전체(그대로 — 빈 값은 "조건 없음") |
| `Object.create({ hots: 'x' })`(상속된 속성) | 전체 | 전체(그대로 — 자기 속성만 본다) |
- 쓸 수 있는 이름: `host`, `method`, `status`, `after`, `limit`. 알림 하나를 판단하는 `matchesFilter`도 같은 규칙이다.
- 오류 문구에는 그 이름과 값을 넣지 않는다. 대시보드에서 들어온 입력이라 무엇이 들어 있을지 모르기 때문이다(다른 오류 문구와 같은 규칙).
