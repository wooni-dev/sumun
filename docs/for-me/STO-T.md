## 한 줄 요약
"지나간 요청을 저장해 두고 다시 보는" 흐름 전체를 테스트로 **먼저** 고정했다. 아직 저장소를 만들지 않아서 이 테스트는 "대기" 상태다. 마지막 작은 단위(STO-4)가 `src/store/attach.ts`를 만들면 실제 검사가 된다.

## 저장소가 하는 일 (개념)
프록시는 요청 하나마다 두 번 알려 준다.
1. **시작 알림**: 요청을 받자마자. 아직 응답은 없다 → 목록에 "진행 중"으로 보인다.
2. **기록(Flow)**: 끝났을 때. 요청·응답의 헤더와 본문(각 1MiB까지)이 들어 있다 → "진행 중"이 결과로 바뀐다.

저장소는 이 둘을 메모리에 모아 두고 세 가지를 한다.
- **알림**: 대시보드(나중의 UI)에 "새 요청이 시작됨 / 끝남 / 오래된 것이 빠짐"을 알려 준다. 이때는 **본문 없는 작은 요약**만 보낸다(결정 S-4). 본문은 크고(JSON으로 바꾸면 4배), 쿠키 같은 민감한 값이 들어 있기 때문이다.
- **목록·필터**: 호스트·메서드·상태 코드로 거른다.
- **상세**: 하나를 고르면 본문까지 있는 **사본**을 준다. 받은 쪽이 고쳐도 저장된 기록은 그대로다.

## 테스트가 확인하는 흐름
```
 [이전 큰 단위의 행동을 다시 한다 — O42]
  ① curl  POST http://127.0.0.1:<평문 목적지>/submit?x=1   (Cookie: k=PLAIN-COOKIE, 본문 hello-sumun) → 200
  ② curl  http://127.0.0.1:<닫힌 포트>/                                                          → 502 (프록시가 만든 응답)
  ③ CONNECT localhost:U → TLS(프록시 CA만 믿음) → GET /hello?q=1 (Cookie: k=TLS-COOKIE)          → 200 secure-hello
                 │
                 ▼  attachStore(store)가 프록시의 시작 알림·기록을 저장소로 연결
 [새 단계: 저장소]
  알림   id마다 start → done 순서. 요약에 "hello-sumun", "secure-hello", 쿠키 값이 없다
  목록   완료 3건, id 오름차순, 모두 같은 runId(이번 실행 식별자)
  필터   method 'post' → ①  /  host 'localhost' → ③(target = https localhost:U /hello?q=1)  /  status 502 → ② (statusFrom 'proxy', error unreachable)
  상세   get(①의 id) → 본문 hello-sumun, Cookie 헤더. 사본의 본문을 0으로 덮어써도 다시 get하면 그대로
  해제   구독을 끊은 뒤 요청은 저장되지만 알림은 오지 않는다
```
두 번째 테스트는 **보관 상한**을 본다. 상한을 1MiB로 작게 두고 약 400KiB짜리 기록(요청 200KiB + 응답 200KiB)을 세 번 만들면 다 들어가지 않는다. 그래서 가장 오래된 첫 번째가 빠지고, `evicted` 알림이 오고, 상세로도 조회되지 않아야 한다. 실제 기본값은 256MiB·10,000건이다(결정 S-1).
