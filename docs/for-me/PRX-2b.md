# [PRX-2b] 기록의 자원 상한·나머지 경계        커밋: 67e36be..(이 문서 커밋)

## 한 줄 요약
PRX-2에서 만든 기록 기능이 **메모리를 터뜨리거나, 이상한 입력에서 틀리게 기록하지 않는지** 확인했다. 사례 13개 중 12개는 이미 올바르게 동작했다. 1개(응답 헤더를 몰래 버림)를 새로 고쳤다. 메모리 사례 4개는 테스트 대신 실측으로 쟀다.

## 새로 고친 1가지: 응답 헤더를 몰래 버림 (G9)
| | 고치기 전 (실측) | 고친 뒤 |
|---|---|---|
| 목적지가 같은 헤더를 1,999개 보냄 | 클라이언트와 기록 모두 **1,000개만** 받음. 뒤에 있던 `Content-Length`도 사라짐 | 전부 받음 |
| 2,500개, 3,500개 | 1,000개만 | 전부 |
| 10,000개 이상(약 50KB) | — | 502 (헤더 전체 크기 제한) |

Node의 HTTP 클라이언트는 응답 헤더가 1,000개를 넘으면 **오류 없이** 나머지를 버린다. 예상은 2,000개였는데 실제로는 1,000개였다(예상 E35 불일치). 디버깅 도구가 "서버가 보낸 것"과 다른 것을 보여 주면 안 되므로 개수 제한을 풀었다(`src/proxy/server.ts:177`). 메모리는 헤더 **크기** 제한(16KB대)이 따로 묶는다. 그래서 10,000개부터는 502가 된다.

## 메모리 실측 (`node scripts/probe/prx2b-memory.mjs`)
기록을 켠 프록시를 별도 프로세스로 띄우고 최대 메모리(RSS)를 쟀다. 기록을 받는 쪽은 받기만 하고 버린다.

| 사례 | 시작 → 최대 | 해석 |
|---|---|---|
| G1 512MB 응답 | 63 → 138MB | 기록이 없던 PRX-1c(142MB)와 같다. 기록은 1MiB만 모은다 |
| G2 1바이트 조각 100만 개 | 67 → 119MB | 조각을 쌓지 않고 한 덩어리에 복사해서 크게 늘지 않는다. 예상(50MB 이하)보다 2MB 넘었다 [추측: GC가 늦게 치움] |
| G5 응답을 읽지 않는 클라이언트 | 67 → 130MB | **역압이 유지된다.** 기록용으로 `'data'`를 엿봐도 `pipe`가 목적지를 멈춘다 |
| G6 연결 200개가 각 1MiB를 보내고 멈춤 | 멈춘 동안 298MB, 끊을 때 475MB | 연결마다 최대 1MiB씩 잡는다. 끊는 순간 기록을 만들며 한 번 더 복사해서 잠깐 더 오른다 |

웹 개발로 비유하면 G5는 **스트림의 `highWaterMark`가 지켜지는지**를 본 것이다. 받는 쪽이 느리면 보내는 쪽도 멈춰야 메모리가 안 쌓인다.

## 이미 잘 되던 것 (회귀 12개, `test/prx/PRX-2b-regression.test.ts`)
- 파서가 거절한 깨진 요청: 400, 기록 없음, 출력 없음(F3, H13)
- 처리 도중 프로세스를 끝내도 기록을 출력하지 않음(F5). 실행 스크립트에 힙 스냅샷 같은 진단 플래그 없음(F7)
- 거짓 `Content-Length: 9999999999`로 메모리를 미리 잡지 않음(G3). gzip은 압축된 그대로 기록(G4: 풀면 50MB인 본문)
- 본문을 보내다 멈추면 정해진 시간 뒤 504로 끝나고 기록 1번(G7). 넘긴 기록을 프록시가 붙잡지 않음(G8: gc 뒤 0개)
- 헤더 값의 앞뒤 공백은 지워지고, 0x80~0xFF는 latin1로 그대로 복원됨(H6). 100-continue, 103 Early Hints 뒤 최종 200을 기록(H16)
- 오래 걸리는 async 구독자가 다음 요청을 늦추지 않음(I3). 구독자 안에서 프록시를 닫아도 안전(I7)

## 범위 밖으로 남긴 것
- 응답 헤더가 크기 제한을 넘어 502가 날 때, 기록의 실패 코드가 `unreachable`(연결 불가)로 남는다. 실제 원인은 "목적지 응답을 해석할 수 없음"이다. 깨진 응답(PRX-1c B11)도 같다 → 실패 코드를 나눌지는 UI에서 실패 이유를 보여 줄 때 정한다(progress.md 범위 밖 문제).
