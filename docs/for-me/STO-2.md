# [STO-2] 보관 상한        커밋: 3ea89d5..(이 문서 커밋)

## 한 줄 요약
저장소가 메모리를 끝없이 쓰지 않게 **세 가지 상한**을 두었다. 넘으면 **먼저 들어온 기록부터** 빼고, 대시보드에 `evicted`로 알린다. 서로 다른 1MiB×2 본문 기록 400건(약 800MiB)을 넣어도 끝에는 127건, 메모리 증가는 약 254MiB에서 멈췄다 [확인됨].

## 세 가지 상한 (결정 S-1·S-2)
| 상한 | 기본값 | 무엇을 세나 |
|---|---|---|
| `maxBytes` | 256MiB | 저장된 본문(요청 + 응답) + 헤더 비용 + 항목 고정 비용. 진행 중 항목(url 등)도 포함 |
| `maxFlows` | 10,000건 | 완료된 기록 수 |
| `maxPending` | 1,000개 | 진행 중(아직 끝나지 않은 요청) 수 |

**왜 바이트를 세나**: 기록 하나가 본문만 최대 2MiB(요청·응답 각 1MiB)다. 건수만 세면 1,000건에 약 2GB가 된다. Node의 Buffer는 JavaScript 힙 밖에 있어서, 힙 한도로는 멈추지 않는다(sto-cases A1).

**무엇으로 세나**
- 본문은 **저장된 길이**(`body.length`)로 센다. 2GB를 내려받아도 저장된 본문은 앞 1MiB뿐이다. 오간 전체 크기(`bodySize`)로 세면, 그 한 건이 상한을 다 차지한 것처럼 보인다(A2).
- 헤더는 **쌍마다 64 + 2×(이름+값 글자 수)** 바이트로 센다. 원문으로는 16KB뿐인 헤더 3,000쌍이 메모리에서는 약 222KB를 쓴다 [확인됨: sto-cases A3].

## 빼는 순서
```
 넣기 ──▶ 알림(start/done) ──▶ ① 진행 중 > 1,000 ?  → 먼저 들어온 진행 중부터 뺀다
                               ② 완료 > 10,000 ?   → 먼저 들어온 완료부터 뺀다
                               ③ 바이트 > 256MiB ? → 상태와 상관없이 먼저 들어온 것부터 뺀다
                               ──▶ 알림 { type: 'evicted', ids: [뺀 id들] } (한 번에)
```
- "먼저 들어온" = 시작 알림(또는 완료)이 저장소에 처음 온 순서다. 진행 중이던 항목은 완료로 바뀌어도 자리를 지킨다.
- **방금 넣은 항목은 빼지 않는다.** 한 건이 상한보다 커도 마지막 하나는 남는다. 기본값에서는 한 건이 최대 약 2MiB라 이런 일은 없다.
- 상한 때문에 뺀 진행 중 요청이 나중에 끝나면, 그 완료 기록은 **버린다**(결정 S-5). 지운 요청이 다시 나타나지 않게 하려는 것이다.

## 실측 (E144)
```
node --expose-gc scripts/probe/sto2-memory.mjs
E144 100건: arrayBuffers +200MiB
E144 200건: arrayBuffers +259MiB
E144 300건: arrayBuffers +313MiB   ← 중간에 상한보다 잠시 높다
E144 400건: arrayBuffers +281MiB
E144 끝: 남은 127건, stats.bytes 254MiB, 뺀 273건, arrayBuffers 증가 254MiB
```
중간 시점(300건)에 +313MiB까지 오른 것은, 뺀 본문의 메모리를 Node가 gc 직후 바로 돌려주지 않아서로 보인다 [추측]. 저장소가 붙잡고 있지 않다는 것은 테스트(A6, WeakRef + gc)로 확인했다. 끝에는 상한 근처로 돌아왔다.
