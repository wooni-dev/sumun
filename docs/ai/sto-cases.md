# [STO] 사례: 저장소(메모리 보관, 새 기록 알림, 조회·필터)

- 출처: 별도 컨텍스트의 검토 에이전트(O10, 2026-11-08). 작업자는 해결안을 알려 주지 않았다. 에이전트에게 준 것은 STO의 목적, 읽을 파일, 찾을 방향뿐이다.
- 에이전트 실행 환경: Node v24.21.0, Windows 11. 실험은 `%TEMP%\sumun-sto-review\`에서만 했고, 저장소 파일·Windows 인증서 저장소·`%LOCALAPPDATA%\sumun`은 쓰지 않았다. 목적지는 모두 127.0.0.1.
- 실험 스크립트는 실측 커밋에서 `scripts/probe/sto-review/`로 옮긴다(O19). 실험 번호 E1~E19는 그 스크립트 출력 줄의 머리표다(이 저장소의 예상 번호 E1xx와는 다르다).
- 배정: 작은 단위 ID(STO-1~4) / **문서** = 테스트 대신 이 문서와 사용자 문서에 동작을 적는다 / **UI** = 대시보드 단계로 넘김 / **범위 밖** = progress.md 범위 밖 문제로.

## 사용자 결정 (2026-11-08)
| # | 항목 | 결정 | 관련 사례 |
|---|---|---|---|
| S-1 | 보관 상한 | 바이트 **256MiB**(저장된 본문 `body.length` + 헤더 이름·값 길이 + 쌍당 고정 비용 추정)와 **10,000건** 둘 다. 먼저 닿는 쪽 기준으로 **가장 오래된 기록부터** 지운다 | A1·A2·A3·A6 |
| S-2 | 진행 중 요청 | 시작 알림은 바로 "진행 중"으로 보관하고 끝 기록이 오면 바꾼다. **CONNECT의 시작 알림은 진행 중에 넣지 않는다**(끝 기록이 올 때만 보관). 진행 중 항목도 상한(1,000개, 바이트 상한에 포함)이 있고 넘으면 오래된 것부터 뺀다. 프록시 코드는 바꾸지 않는다 | A4·A5·A8·B9 |
| S-3 | 상태 코드 필터 | **브라우저가 받은 코드**: 목적지 응답이 있으면 그 코드, 없으면 프록시가 보낸 `error.status`. 요약에 출처(`upstream`·`proxy`)를 함께 둔다 | D7 |
| S-4 | 넘길 모양 | 알림과 목록에는 **본문 없는 작은 요약**, 상세는 id로 조회할 때 **본문까지 복사한 사본** | A9·C9·C10·D11 |

## 추천대로 진행한 것 (사용자에게 질문하지 않음 — STO 보고서 결정 항목에 올린다)

|---|---|---|---|
| S-5 | 지운 뒤 늦게 온 끝 기록 | 모두 지우기·상한으로 뺀 진행 중 항목의 끝 기록은 **버린다** | B5 |
| S-6 | 호스트 필터 | 저장소가 필터할 때 맞춘다: 대소문자·끝 점 무시, IPv6는 URL 규칙으로 정규화, 입력의 국제화 도메인은 punycode로, `host:port` 입력이면 포트도 비교. 같은 호스트와 그 하위 도메인이 걸린다. 기준 칸은 `request.target`(없으면 호스트 필터에 걸리지 않음) | D1~D6 |
| S-7 | 여러 프록시 공유 | 저장소 하나에 프록시 하나. 두 번째 연결은 오류 | B3·F2 |
| S-8 | 메서드 필터·CONNECT | 대소문자 무시. CONNECT 기록도 보관(보일지는 UI) | D8 |
| S-9 | 재시작 구분 | 저장소마다 실행 식별자(`runId`)를 두고 요약에 넣는다 | B4 |
| S-10 | 구독자 격리 | 구독자의 throw·reject는 저장 상태와 다른 구독자, 프록시에 번지지 않고 **아무것도 출력하지 않는다**(셈만). 알림 중 추가·해제는 다음 알림부터 | C2~C8 |

## A. 메모리 고갈·해제
| ID | 상황 | 왜 문제인가 | 기대 동작 | 근거 |
|---|---|---|---|---|
| A1 | 건수 상한만 두고 바이트 상한이 없음. 1,000건 × (요청 1MiB + 응답 1MiB) | 약 2GB. Buffer는 힙 밖(arrayBuffers)이라 V8 힙 한도에 걸리지 않는다 | 기록 전체의 바이트에 상한 | [확인됨: e4-memory E16 — 1MiB 300건 arrayBuffers +300MB] / prx2-cases J5 |
| A2 | 바이트를 `bodySize`(오간 전체 크기)로 셈 | 2GB를 내려받아도 저장 본문은 1MiB. 한 건이 상한을 다 차지한 것으로 보인다 | 저장된 바이트(`body.length`)로 센다 | [추측: flow.ts] |
| A3 | 헤더가 많은 기록(16KB 안 약 3,000쌍)을 원문 바이트로만 셈 | `[string,string][]`는 힙에서 건당 약 222KB | 메모리 계산에 헤더의 실제 비용 | [확인됨: E17 — 3,000쌍 200건 힙 +43.4MB] |
| A4 | 복호화 CONNECT의 시작 알림을 "진행 중"으로 두고 끝을 기다림 | 터널 안에 요청이 있으면 CONNECT의 끝 기록이 오지 않는다. HTTPS 사이트마다 진행 중 칸이 영원히 는다 | 끝이 오지 않는 시작 알림이 끝없이 쌓이지 않는다 | [확인됨: e3-mitm E8b — 시작 `1:CONNECT 2:GET`, 끝 `2:GET:200`] |
| A5 | 진행 중 요청 수에 상한 없음 | 요청 전체 시간 제한 없음(`requestTimeout: 0`), SSE·롱폴, 몇 시간짜리 불투명 터널 | 오래 열린 요청도 전체 상한 안 | [추측: server.ts] |
| A6 | 지웠지만 다른 색인(호스트별 배열, 캐시)에 참조가 남음 | 메모리가 풀리지 않는다 | 모든 색인에서 빠지고 메모리가 실제로 준다 | [확인됨: E16 — 색인이 붙잡으면 +300MB 그대로, 비우면 +0] |
| A7 | 미리보기용 `body.subarray(0, 100)` 보관 | 원본 1MiB 전체를 붙잡는다 | 일부만 보관하면 그 크기만 | [확인됨: E1 — 100개 → +100MB] |
| A8 | 시작 알림의 `request`를 끝 기록과 따로 보관 | 헤더 배열이 두 벌 | 끝이 오면 시작 사본은 남지 않는다 | [추측: server.ts] |
| A9 | 목록 전체를 `JSON.stringify` | Buffer가 `{"type":"Buffer","data":[…]}`로 약 4배, 200건 × 1MiB면 RangeError | 큰 목록 조회에도 예외·폭증 없음 | [확인됨: E3 — 4.00배, E3b — `RangeError Invalid string length`] |
| A10 | 느린 대시보드로 보낼 데이터가 쌓임 | 지운 기록도 전송 큐가 사본으로 붙잡는다 | 구독자가 느려도 저장소 쪽 메모리는 상한 안 | [추측] |

## 에이전트가 낸 결정 질문(선택지만, 추천 없음)
1. 상한 기준: 건수만 / 바이트만 / 둘 다. 바이트에 헤더 비용 포함 여부
2. 상한 도달: 가장 오래된 것부터 지움 / 본문만 비우고 요약 유지 / 새 기록 거부
3. 끝이 오지 않는 시작 알림: 저장 안 함 / 진행 중으로 계속 / 일정 시간 뒤 정리 / 프록시가 CONNECT 끝 기록을 보내게 변경
4. 지운 뒤 늦게 온 끝 기록: 버림 / 새로 넣음
5. 상태 코드 필터에 프록시가 만든 응답(`error.status`) 포함 여부
6. 호스트 표기를 어디서 맞출지: 저장소 필터 / 프록시 기록 생성 / 원문 그대로
7. 여러 프록시 공유 허용 여부
8. 구독자에게 줄 것: 저장 객체 그대로 / 사본 / 고칠 수 없는 객체
9. CONNECT 기록을 목록에 보일지
10. 프록시 재시작 뒤 구분: 실행마다 식별자 / 다시 연결하면 목록 비움
