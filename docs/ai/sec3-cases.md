# [SEC-3] 사례: 루트 CA 등록·해제·상태 명령

- 출처: 별도 컨텍스트의 검토 에이전트(O10, 2026-11-08). 작업자는 해결안을 알려 주지 않았다. 에이전트에게는 Windows 인증서 저장소를 바꾸는 명령을 금지했고, 읽기(`certutil -user -store`, `-dump`, `-?`, `Get-ChildItem Cert:`, 레지스트리 읽기)만 했다.
- 에이전트 환경 [확인됨]: 관리자 아님·UAC 켜짐, Chrome 156, Firefox 없음, curl 두 개(`C:\Windows\system32\curl`, Git Bash `/mingw64/bin/curl`) 모두 8.21.0 Schannel, `HKCU\…\Root\ProtectedRoots` 있음, 그룹 정책 키 없음.
- 배정: **3** = 이 단위의 테스트(가짜 저장소·실행기) / **실측** = 사용자가 직접 실행하는 실제 등록·해제와 브라우저 확인(O31) / **문서** = 테스트 대신 사용자 문서에 적는다 / **범위 밖**.

## 먼저 볼 실측 (에이전트, [확인됨])
1. 지금 `loadOrCreateCA`는 인증서가 2개 든 `ca-cert.pem`, 앞에 ESC가 섞인 잡문·깨진 PEM 블록이 붙은 파일도 받는다. Node `X509Certificate`·forge·`certutil -dump`는 첫 블록만 본다.
2. certutil의 CertId는 지문 전용이 아니다(`certutil -store -?`: 일련 번호, SHA-1, 공개 키 해시, 인덱스, OID, 주체 이름 … "일치하는 항목이 여러 개 있을 수 있습니다"). 컴퓨터 Root에서 serverAuth OID 하나가 7개에 맞았다. 콜론 구분 지문(`CD:D4:…`)은 `0x80090011 NTE_NOT_FOUND`.
3. PowerShell `Cert:\CurrentUser\Root`는 컴퓨터 저장소를 합쳐 보인다(37개). 사용자 물리 저장소(`certutil -user -store Root`, `HKCU\…\SystemCertificates\Root\Certificates`)는 0개.
4. certutil 출력은 CP949(콘솔 65001이어도). 날짜는 현지 오전/오후. 실패 종료 코드는 부호 없는 HRESULT(`2148073489`).
5. 이름의 U+202E는 Node `x.subject`가 그대로 둔다. `certutil -dump`는 ESC·줄바꿈을 그대로 찍는다.
6. 정션 폴더도 `loadOrCreateCA`가 받는다.
7. 현재 폴더의 가짜 `certutil.exe`는 이 PC에서 실행되지 않았다. 다만 PATH에 사용자가 쓸 수 있는 폴더가 있다. `src/ca/ca.ts`의 `SYS`는 `SystemRoot`를 믿는다.

## 테스트로 만들기 어려운 사례 (에이전트 의견)
- Windows 확인 창의 내용·"아니요" 종료 코드·Ctrl+C 뒤 창(C5, D4, D8, E2) — 실제 저장소 변경이 필요하다. 사용자가 직접 실행하는 실측으로만.
- 여러 인증서 PEM을 `-addstore`가 몇 개 넣는지, `-delstore`가 여러 개 맞으면 모두 지우는지(A1, B2) — 설계(DER 1개, 지문 + 겹침 검사)로 이 미지수를 피한다.
- 브라우저 정책(G1, G4~G7), 그룹 정책(G2), 비한국어 Windows(D6), 관리자 터미널(A9, A10)의 실제 동작.
