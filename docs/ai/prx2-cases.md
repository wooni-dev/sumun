# PRX-2 보안·경계 사례 (O10: 검토 에이전트 제안)

출처: 2026-11-07, 별도 컨텍스트의 검토 에이전트가 **명세만 보고** 제안 [추측: 코드 없음, 실행 안 함]. 작업자의 구현안은 알려 주지 않았다.
명세: 요청마다 Flow를 만든다 / 메모리에만 / 본문은 각 1MB까지 기록하고 "잘림" 표시(중계는 전체) / 민감한 값은 원본 그대로 기록하되 기록 밖으로 새면 안 됨 / 구독자 콜백으로 전달.
배정: **2** = PRX-2, **2b** = PRX-2b(자원·나머지 경계), **나중** = 표시한 단계에서 다시 본다.

공통 방법(검토자 제안): 매번 새로 만드는 표식 문자열 `SUMUN-SECRET-<난수>`를 Cookie, Authorization, 쿼리, 본문, Set-Cookie에 넣고, 기록 밖(콘솔, 응답, 디스크, 다른 연결)에 나타나지 않는지 본다.

## G. 메모리·자원 고갈 (전부 2b — 측정 위주)
G1 2GB 본문에도 기록 메모리 1MB에서 멈춤 / G2 1바이트 청크 100만 개 / G3 거짓 `Content-Length: 9999999999`로 미리 할당하지 않음 / G4 gzip 폭탄 — 기록 단계에서 풀지 않음 / G5 클라이언트가 읽지 않을 때 역압 유지(가장 중요한 회귀 후보) / G6 동시 연결 × 2MB / G7 끝나지 않는 요청 본문 / G8 완료된 Flow를 프록시가 붙잡지 않음 / G9 헤더 3,000개·큰 헤더

## I. 구독자(콜백)

|---|---|---|---|
| I1 | 구독자가 `throw new Error(JSON.stringify(flow))` | 중계 정상, 프록시 생존, 다음 요청 정상, 출력에 표식 없음 | 2 |

## J. 나중 단계에서 다시 볼 것
J1 대시보드 XSS(본문을 텍스트로만, CSP) → UI / J2 DNS 리바인딩·CSRF(Host·Origin 검사, CVE-2018-5702) → UI / J3 WebSocket 하이재킹(Origin) → UI / J4 시스템 프록시로 다른 프로그램 트래픽까지 기록 → 설정 단계 / J5 1,000건 × 2MB ≈ 2GB → STO에서 바이트 상한 / J6 HAR·cURL 복사 내보내기 → UI / J7 HTTP/2·HTTPS에서 "원문" 개념 → TLS / J8 텔레메트리 라이브러리 금지, F 사례를 계속 회귀로 유지 → 전체

## 결정 항목 (Claude 추천으로 진행, 보고서에 올림)
| # | 항목 | 정한 것 | 이유 |
|---|---|---|---|
| D1 | 1MB의 정의 | 1,048,576바이트(1MiB), 상수 `FLOW_BODY_LIMIT` | 상수 하나로 바꿀 수 있다 |
| D2 | 본문 형태 | chunked는 **디코딩된 본문**, gzip 등은 **압축된 원본** | Node가 주는 형태 / 기록 단계에서 압축을 풀면 폭탄(G4) |
| D3 | 전체 크기 | 잘려도 실제 전체 바이트 수를 기록(`bodySize`) | "잘림"만으로는 크기를 모른다 |
| D4 | 거부된 요청 | 요청 처리기에 들어온 요청은 모두 기록(400·501·508·502·504). 파서 오류·CONNECT는 기록하지 않음 | 왜 막혔는지 보는 것도 디버깅이다. 파서 오류는 원본 바이트를 다뤄야 해서 2b에서 다시 본다 |
| D5 | 호출 시점 | 완료(또는 실패) 때 **1번** | 시작 이벤트는 UI에서 필요해지면 추가한다(추가만 하면 되는 변경) |
| D6 | 구독자 예외 | 무시하고 고정 문구 한 줄만 stderr에 | 기록 기능 때문에 중계가 죽으면 안 된다 |
| D7 | 진행 중 기록 전체 상한 | **두지 않음**(PRX-2b 결정). STO에서 전체 바이트 상한(J5)을 정할 때 다시 본다 | 측정: 연결 200개 × 1MiB에서 멈춤 → 최대 475MB(scripts/probe/prx2b-memory.mjs). 브라우저의 프록시당 동시 연결은 수십 개라 [추측] 실제 최악은 약 64MB |
| D8 | 헤더 원문 수준 | Node `rawHeaders` 수준(앞뒤 공백 제거, latin1) | 바이트 원문은 직접 파서가 필요하다 |
| D9 | 1xx·트레일러 | 기록하지 않음 | 2b에서 다시 본다 |
| D10 | 실제로 보낸 헤더 | 따로 기록하지 않음(클라이언트가 보낸 원문만) | 차이는 hop-by-hop 규칙으로 정해져 있다 |
| D11 | 구독자에게 주는 객체 | 구독자는 하나. 중계가 끝난 뒤 호출하고, 본문은 중계 청크와 공유하지 않는 별도 메모리 | 변조해도 중계에 영향이 없다(I4, F9) |
| D12 | 로그 허용 목록 | 프록시는 아무것도 출력하지 않는다. 예외: 구독자 오류의 고정 문구 한 줄(오류 내용은 출력하지 않음) | F 사례의 기준을 분명하게 |

## PRX-2b 처리 결과 (2026-11-07)
- 새 동작 1개: G9(Node 클라이언트가 응답 헤더 1,000개 넘게 몰래 버림 → 개수 제한 해제). 회귀 12개: F3, F5, F7, G3, G4, G7, G8, H6, H13, H16 ×2, I3, I7.
- 실측(테스트 아님): G1, G2, G5, G6 → `scripts/probe/prx2b-memory.mjs`.
- I6(구독자가 프록시를 거쳐 요청): 테스트하지 않고 규칙으로 남긴다 — **구독자(STO, UI) 안에서 이 프록시를 거치는 요청을 만들지 않는다.** 그 요청은 새 요청이라 Via 루프 감지가 막을 대상이 아니다.
- H16의 시계 변경 사례: 소요 시간은 단조 시계(`performance.now`)로 잰다(PRX-2에서 반영). 시계를 실제로 바꾸는 시험은 하지 않았다.
