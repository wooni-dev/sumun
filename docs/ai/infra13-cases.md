## 한계
- L1 표시 파일 또는 `"branch"` 키를 지우면 규칙 D가 꺼진다. 저장소에 커밋되어 git 이력에 남고, 테스트가 "이 저장소 설정에 키가 있다"를 본다.
- L2 실행 뒤 검사는 이미 생긴 커밋을 알릴 뿐이다. 되돌리기는 사용자가 정한다.
- L3 `.git/` 직접 쓰기는 실행 전에 보지 않는다. HEAD가 바뀌면 실행 뒤 검사가 브랜치 변화로 본다.
- L4 도구 두 개를 동시에 돌리면 판정 시점과 커밋 시점의 브랜치가 다를 수 있고 기록이 덮인다.
- L5 앞 호출에서 브랜치를 바꾸고 다음 호출에서 커밋하는 것은 정상 작업과 구별되지 않는다(사례 3).
- L6 같은 ID의 옛 메시지 파일(사례 31)은 통과한다 — 지침(O54)이 막는다.
- L7 reflog가 꺼져 있거나 명령 도중 지워지면 실행 뒤 검사가 새 커밋을 놓친다.
- L8 리베이스·cherry-pick으로 다시 만든 정당한 다른 ID 커밋(F12)도 알린다.
- L9 실행 뒤 검사의 기존 시각 필터(규칙 C)는 날짜를 바꾼 커밋을 놓친다(사례 25). 규칙 D는 reflog 개수로 보므로 영향이 없다. 실행 전에는 같은 명령의 환경 변수 설정을 막는다.
- L10 실행 뒤에는 병합 커밋을 보지 않는다(INFRA-11 D4). 병합 메시지는 실행 전 `git merge`에서만 본다.
- L11 `feat`가 아닌 브랜치(`probe/…`)의 커밋은 보지 않는다. 그 브랜치를 병합해 들여오면 남는다.
